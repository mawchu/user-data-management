# 0004 欄式 TypedArray 加字典編碼

- 狀態：採用
- 階段：3 千萬筆資料層

## 背景
mock 要真的能對一千萬筆排序、搜尋、修改，又不能讓瀏覽器吃掉好幾 GB 記憶體。

## 決策
- **欄式儲存**：不用一千萬個 `{ userName, age, ... }` 物件，而是每個欄位一條 TypedArray（固定型別的數字陣列），例如 `age` 存成 `Uint8Array`。
- **字典編碼**：字串欄位只存「編號」。例如 Position 只有 12 種值，就存成 `["Frontend Engineer", ...]`，每列只記 0 到 11。反查「這個字串是幾號」時用 `Map<string, number>`。
- 日期存成「從 1950-01-01 起算的天數」（`Uint16Array`）。
- 每筆共 7 bytes，一千萬筆約 70MB。

## 為什麼不用 Map 或物件陣列（實測，Node 22，1,000 萬筆）
| | TypedArray | 每筆一個物件，存進 Map |
|---|---|---|
| 記憶體 | 70 MB | 1,190 MB |
| 產生資料 | 0.04 秒 | 11.8 秒 |
| 用 id 查 100 萬次 | 0.014 秒 | 1.25 秒 |
| 依 Age 排序 | 0.04 秒 | 1.8 秒 |
| 搜尋 engineer | 0.02 秒 | 0.49 秒 |

- id 本身就是連續整數，陣列的「第 id−1 格」就是最快的查表方式。
- 排序和搜尋都要掃過整批資料。連續的數字陣列掃起來，比散落在記憶體各處的物件快得多。
- V8 的 Map 有大約 1,670 萬筆的上限。

Map 仍然用在適合的地方：字典的「字串查編號」、釘選清單 `Map<id, 位置>`。

## 為什麼不用 tree
tree 的每個節點都是一個物件，記憶體成本跟 Map 相近。題目要的搜尋是「包含」（例如 chen 也要找到 Cheng），B-tree 和 trie 只擅長範圍與前綴。另外，資料幾乎不變，用不到 tree「插入時保持有序」的強項。

## 代價
- 每個字串欄位的不同值有上限：姓名 65,535 種，職位和地點各 255 種。超過時回 507。
- 這個做法依賴「每欄不同值很少」這個前提。若不成立（例如精確到秒的時間），要改用 B-tree 或排序後的索引。
