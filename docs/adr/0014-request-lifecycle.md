# 0014 請求生命週期：失敗停止、保留舊資料、第一批快取、429

- 狀態：採用
- 階段：5 API 層

## 背景
重新審查時發現，載入失敗會無限重送請求。原因是 `loadMore` 失敗後 `loading` 變回 false，表格的預先載入 `watchEffect` 馬上又觸發一次。模擬後端一直回 500、延遲 5ms 時，1 秒內送出 172 個請求。如果 50 個人同時遇到，就會是一波請求風暴，正好就是 b 題描述的情況。

## 決策
都寫在 `src/composables/useUserList.ts`：
1. **失敗就停下來**：有 `error` 時 `loadMore` 直接返回，表格的預先載入也不觸發。畫面底部顯示錯誤和「重試」按鈕，由使用者決定什麼時候再送。
2. **換條件時保留舊資料**：`reload()` 不再先清空列表，而是標記 `stale`，表格變淡並且不能操作。新的第一批回來後才一次換掉，畫面不會閃成空白。
3. **第一批快取**：用查詢條件當 key，保留 30 秒，最多 20 組，超過時刪掉最久沒用的。在幾個排序之間來回切換時不用重送請求。新增、更新、刪除之後清空，避免看到舊資料。
4. **429**：依 `Retry-After` 等待（最多 10 秒），等待期間顯示「n 秒後自動重試」，然後自動重試一次。再失敗就進入第 1 點的狀態。等待可以被取消，換條件時不會繼續等。

## 放棄的選項
- **合併相同的請求**（相同條件共用同一個進行中的請求）：同一個畫面同時只有一個查詢，換條件時舊的會被取消，所以不會出現兩個相同的請求在進行中，做了也沒有效果。
- **失敗後自動指數退避重試**：使用者看不到發生了什麼事，網路恢復的時間點也無法預測。改成手動重試，行為比較好預期。

## 代價
- 快取最多讓使用者看到 30 秒前的第一批；但只要自己修改過資料就會清空。
- `stale` 期間不能操作列表，要等新資料回來。

## 驗證
`tests/use-user-list.test.ts`：
- 失敗後只送 1 個請求，按重試才恢復。
- `stale` 期間畫面上還是舊資料，新的第一批回來後才換掉。
- 切回快取過的條件不送請求，修改資料後快取失效。
- 429 時顯示提示，等待後重試成功。
