# 0013 cursor 改成 keyset（排序值 + id）

- 狀態：採用（取代 [0003](0003-cursor-infinite-scroll.md) 中 cursor 的實作方式）
- 階段：2 載入方式

## 背景
原本的 cursor 是「快照中的位置」，刪除一筆時前端要把 cursor 減 1。重新審查時實測到一個競態問題：下一批還在路上時刪除一筆，請求回來後會用新的 `nextCursor` 蓋掉減 1 的修正。1,500 筆資料最後只載入 1,498 筆，#501 不見了。

另外，mock 只有一份共用的快照。多人使用時，別人的查詢會把它換掉，位置就對不上了。

## 決策
- cursor 改成「上一批最後一筆的排序值 + id」。後端用二分搜尋找到排在它後面的第一筆（`src/mock/db.ts` 的 `positionAfter`）。
- 前端刪除時不再修改 cursor，`useUserList` 裡相關的程式碼整段移除。
- 快照建立後才被刪除的列不從快照搬走，輸出時跳過即可。快照另外記下建立當下的排序值，之後有人修改也不會影響二分搜尋。

## 放棄的選項
- 保留位置 cursor，等載入完成後再套用刪除：要多維護一個「待套用」的佇列，而且仍然解決不了快照被別人換掉的問題。

## 代價
- 捲動途中新增、且排在已載入範圍內的資料，要重新查詢才會出現（寫在 [API 契約](../api.md)）。
- mock 多一份排序值陣列，1,000 萬筆時記憶體從約 183MB 增加到約 253MB（`npm run perf`）。這是測試環境的成本。

## 驗證
- `tests/use-user-list.test.ts`「載入下一批的途中刪除一筆」：1,500 筆刪掉 1 筆，結果剛好 1,499 筆，沒有重複。
- `tests/db.test.ts`：分別刪掉已載入的一筆、cursor 指向的那一筆、還沒載入的一筆，接起來的結果和參考實作一致；別人的查詢換掉快照後，我的下一批仍然接得上。
