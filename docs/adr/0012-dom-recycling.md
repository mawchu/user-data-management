# 0012 虛擬捲動改成 DOM 回收（v2）

- 狀態：採用（取代 [0007](0007-virtual-scroll.md)）
- 階段：4 畫面
- 比較文件：[自己實作回收 vs 套件](../virtual-scroll-options.md)

## 背景
v1（ADR 0007）只渲染看得到的約 25 列，但用**資料 id 當 key**：每往下捲 1 列，Vue 刪掉最上面那列的 DOM、替新進來的列建一個新的 DOM。

討論時提出一個問題：「既然 DOM 數量固定，為什麼不重複使用同一組 DOM，只換內容？」這個做法叫 **DOM 回收（DOM recycling）**，`vue-virtual-scroller` 的 `RecycleScroller`、Android 的 `RecyclerView` 都是這樣做的。

## 量測（事實）
`npm run bench:scroll`（headless Chromium，30 列可視、2 萬筆資料，每種跑 4 次取中位數；兩次執行的範圍）：

| 每捲一步的耗時 | v1：id 當 key | 格子編號當 key（簡單版） | v2：每格各自定位的回收 |
|---|---|---|---|
| 純 div 列，慢慢捲 | 0.10–0.14ms | 0.11–0.16ms | **0.06ms** |
| 純 div 列，快速拖曳 | 0.24–0.85ms | 0.09–0.14ms | 0.10–0.17ms |
| 元件列，慢慢捲 | 0.10ms | 0.24–0.30ms | **0.04–0.05ms** |
| 元件列，快速拖曳 | **1.8–3.2ms** | 0.27–0.28ms | 0.29–0.39ms |

解讀：
- 回收在慢慢捲時約快 2 倍；快速拖曳時，v1 最慢（每步都要建立、銷毀整批 DOM）。
- 「直接把 key 換成格子編號」的簡單版，慢慢捲時反而比 v1 慢，因為整塊位移，30 格每一格都要更新內容。所以 v2 讓**每格各自定位**，捲 1 列只有 1 格換資料。
- 所有數字都遠低於一幀的 16.7ms。**本專案的純 div 列，使用者感覺不到差別**；差距在列變複雜（元件、圖片）時才會放大。

## 決策
`UserTable.vue` 改成 DOM 回收：
1. 格子數固定：`poolSize = ceil(視窗高 / 44) + 上下緩衝 8 × 2 + 1`。
2. 第 `rowIndex` 列固定交給第 `rowIndex % poolSize` 格（key 是格子編號），每格用自己的 `translateY(rowIndex × 44px)` 定位。
3. 往下捲 1 列時，只有捲出去的那一格搬到最下面換資料；其他格子的內容和位置都不變。
4. **處理回收的副作用：焦點**。格子換成別筆資料時，如果焦點還在那格的按鈕上，就把焦點移開，避免使用者按 Enter 操作到另一個人。
5. 列裡不放任何自己的狀態。選取高亮本來就存成 `selectedId`（以 id 判斷），不受回收影響。

## 和 v1 的差異
| | v1（ADR 0007） | v2（本決策） |
|---|---|---|
| key | 資料 id | 格子編號（`rowIndex % poolSize`） |
| 捲 1 列時 | 刪 1 個 DOM、建 1 個 DOM，其餘整塊位移 | 1 格換內容和位置，其餘不動 |
| 定位方式 | 外層一塊 `translateY(start × 44)` | 每格各自 `translateY(rowIndex × 44)` |
| DOM 順序 | 等於畫面順序 | **不等於**畫面順序，靠 `aria-rowindex` 標示 |
| 焦點 | 天生正確（DOM 跟著資料走） | 要額外處理（換人時移開焦點） |
| 列內狀態 | 天生正確 | 必須存在以 id 為索引的資料裡 |
| 程式量 | 約 30 行 | 約 60 行 |

v1 原樣保留在 `src/components/legacy/UserTableKeyed.vue`，方便對照。

## 為什麼採用 v2
- 實測慢慢捲快約 2 倍，快速拖曳不再每步建立、銷毀 DOM。
- 這是從「DOM 數量固定」推導出的優化。實作過程也完整走過「量測 → 實作 → 處理副作用（焦點）→ 驗證」，比較能說明取捨。
- 程式量增加約 30 行，在可接受範圍內。

## 放棄的選項
- **維持 v1**：最簡單，效能也足夠。但會失去展示上述判斷過程的機會。
- **改用 `vue-virtual-scroller` 的 `RecycleScroller`**：原理相同，而且支援可變列高、各種邊界情況都處理過。但要重寫表格、配合它的元件結構；**焦點錯位它也不會替你處理**（查過 3.0.5 原始碼，沒有任何焦點相關邏輯）。詳見比較文件。

## 代價
- DOM 順序和畫面順序不同。螢幕閱讀器依 DOM 順序朗讀，所以加上 `aria-rowindex`；測試也要依 `aria-rowindex` 排序後再比對。
- 之後如果列裡加入勾選框、輸入框等狀態，一律存成 `Set<id>` 或 `Map<id, 值>`，不能存在列本身。
- 仍然只支援固定列高。需要可變列高時，改用 `DynamicScroller`。

## 驗證
- e2e：捲動 40 列後，34 個 DOM 元素全部沿用（同一批節點），只換內容。
- e2e：焦點在刪除鈕上時，列還在畫面上就保留焦點；格子換成別人後，焦點自動移開。
- 原本的 15 步 e2e 全部通過，單元測試 33 項通過。
- `npm run bench:scroll` 可重跑上面的量測。
