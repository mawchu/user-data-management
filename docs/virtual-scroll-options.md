# 虛擬捲動的 DOM 回收：A 自己實作 vs B 套件

> 結論：本專案採用 **A（自己實作）**，決策紀錄見 [ADR 0012](adr/0012-dom-recycling.md)。
> B 的原理是讀 `vue-virtual-scroller` 3.0.5（2026-08 發布）的原始碼整理的，標「事實」的部分都有對照過程式碼。

## 共同的出發點
兩者都在解決同一件事：**DOM 數量固定，捲動時不要一直建立、刪除 DOM，而是把捲出去的元素拿來重用。**
差別在「誰來寫」，以及「要處理多少種情況」。

---

## A：自己實作（本專案採用）

位置：`src/components/UserTable.vue`（約 60 行）

### 原理
```
poolSize = ceil(視窗高 / 44) + 8 × 2 + 1        ← 格子數固定，例如 34 格
第 rowIndex 列 → 第 rowIndex % poolSize 格      ← 固定的對應規則
每格 transform: translateY(rowIndex × 44px)     ← 每格自己定位
```
往下捲 1 列（start 從 100 變 101）：
- 第 100 列捲出去，它佔用的是第 `100 % 34 = 32` 格。
- 新進來的第 134 列，剛好也對應第 `134 % 34 = 32` 格。
- 所以只有第 32 格換內容、搬到最下面，其他 33 格完全不動。

### 自己補上的副作用處理
- **焦點**：格子換成別筆資料時，如果焦點在那格的按鈕上，就把焦點移開（`UserTable.vue` 的 `watch(slots, …)`）。
- **列內狀態**：列裡不存任何狀態，選取高亮用 `selectedId === row.id` 判斷。

## B：套件 `vue-virtual-scroller` 的 `RecycleScroller`

### 原理（事實，讀原始碼 `src/composables/useRecycleScroller.ts`）
1. **每個畫面元素是一個「view」**：裡面記著目前顯示哪一筆資料（`item`）、位置（`position`），以及 `nr = { index, used, key, type }`。
2. **列離開可視範圍時不銷毀**：`removeAndRecycleView()` 把 view 放進「回收池」，標成 `used = false`，並把位置設到 `-999999`。元素還在 DOM 裡，只是被移到畫面外。
3. **新列進入時從回收池拿**：`getRecycledView(type)` 從池子裡 `pop()` 一個 view，換上新資料、更新 `position`。池子空了才建立新的 view。
4. **定位**：每個 view 用 `transform: translateY(position px)` 定位，和 A 一樣。
5. **緩衝**：`buffer` 參數（單位 px）讓可視範圍上下多算一段，快速捲動時不會閃白。
6. **捲動事件**：用 passive 監聽，再用 `requestAnimationFrame` 合併成每幀最多算一次。
7. **不同種類的列各有一個池子**（`type`）：例如「標題列」和「資料列」不會互相重用。
8. **列內狀態**：提供 `useIdState()`，用資料 id 為每列保存狀態，避免「狀態跟著格子跑」。這是套件對狀態污染問題的官方解法。
9. **可變列高**：另有 `DynamicScroller`，用 `ResizeObserver` 量出每列實際高度後再計算位置。

### 套件沒有處理的（事實）
- **焦點錯位**：搜尋 3.0.5 原始碼，沒有任何 `focus`、`blur`、`activeElement` 相關邏輯。用 B 也要自己處理，和 A 一樣。

### A 和 B 的對應規則不同
- A：**固定公式** `rowIndex % poolSize`，第幾列一定用第幾格。
- B：**自由取用**，哪個 view 先被回收，就先被拿去用。比較有彈性，能支援可變列高、不同種類的列。

## 比較

| | A 自己實作 | B 套件 RecycleScroller |
|---|---|---|
| 回收原理 | 固定公式 `rowIndex % poolSize` | 回收池，先回收的先用 |
| 程式量 | 約 60 行，全部看得懂 | 加一個依賴；表格要改寫成它的元件結構 |
| 可變列高 | 不支援 | 支援（DynamicScroller） |
| 不同種類的列 | 不支援 | 支援（依 type 分池） |
| 列內狀態 | 自己存成 `Set<id>` / `Map<id, 值>` | 有 `useIdState()` 可以用 |
| 焦點錯位 | 已自己處理 | **不處理**，要自己補 |
| 無限捲動、cursor、刪除後 cursor 減 1 | 在 `useUserList.ts`，不受影響 | 一樣在 `useUserList.ts`，套件不管資料 |
| 邊界情況（視窗縮放、捲到很遠、捲軸高度上限） | 只處理了本專案遇到的 | 經過大量使用者驗證 |
| 面試說服力 | 能完整說明原理與取捨 | 「不重造輪子」，但要能說明原理 |
| 適合的情境 | 固定列高、列結構單純、想掌握每一行程式 | 真實產品、列高不固定、列很複雜 |

## 為什麼這個專案選 A
1. 列高固定、列結構單純，用不到 B 的可變列高和多種列。
2. B 也不處理焦點，選 B 不會少寫這段。
3. 改動小（約 30 行），而且每一行都能在面試時解釋。
4. 實測效能和 B 的做法同等級（兩者都是「每格各自定位的回收」），見 ADR 0012 的量測表。

**什麼時候改用 B**：列高需要依內容變化（例如備註欄自動換行），或是列裡有大量元件、圖片。這時 B 處理過的邊界情況，會比自己補省事得多。
