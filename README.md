# Q2

Vue 3 + TypeScript 實作的使用者資料管理後台。前端的重點有四個：查詢請求的生命週期與競態問題、大量資料的渲染與記憶體控制、新增／刪除／更新／搜尋／排序／釘選之後畫面狀態的一致性，以及多人同時修改時的衝突處理。

搜尋和排序要對全部資料才算正確，所以交給後端。前端負責的是怎麼發請求、怎麼收結果，以及資料衝突時怎麼處理。因為沒有真的 API，我另外寫了一個能撐一千萬筆的 mock 後端（放在 Web Worker），讓前端在接近題目的資料量下測試；前後端之間的約定寫在 [docs/api.md](docs/api.md)。接真 API 時刪掉 `main.ts` 裡的 `setupMock()` 即可。

線上 demo：<https://mawchu.github.io/user-data-management/>（預設 1,000 萬筆，開啟時會先在瀏覽器裡產生資料；網址加 `?size=5000` 可以用較少資料試用）。

程式碼導讀在 [docs/code-map.md](docs/code-map.md)，各項決定的考量記在 [docs/adr/](docs/adr/README.md)。

### a. 實作

#### 執行
```bash
npm install
npm run dev          # 開發模式，打開 http://localhost:5173
npm test             # 單元測試（49 項）
npm run perf         # 10,000,000 筆 mock 後端效能量測
npm run bench:scroll # 虛擬捲動三種寫法的效能比較（v1 / 簡單版 / DOM 回收）
npm run build && npm run preview   # 正式建置後預覽（http://localhost:4173）
node e2e/run.mjs     # 瀏覽器端對端測試（需先啟動 preview；Chromium 路徑用 CHROMIUM 環境變數指定）
```
除錯時可以在網址加 `?size=5000`，改用比較少的資料；加 `?rateLimit=2` 可以手動觸發後端限流（429）。

#### 功能
- 新增資料：新增成功後放在最上面並標示「新增」，下次重新查詢時才依排序規則排到正確位置。
- 刪除、更新都會跳確認視窗；更新會列出「原本 / 改為」再確認。前後端共用同一份欄位驗證。
- 一個搜尋框搜尋所有欄位（停止輸入 300ms 才查詢），點表頭可排序任一欄；手機改用排序選單。
- 無限捲動：每次載入 500 筆，捲到離底部剩 150 列時先抓下一批。
- 釘選：指定某筆資料固定在第幾列，之後不管怎麼排序都在那個位置。釘選是個人設定，存在瀏覽器裡，不影響其他人。
- 桌機用表格，手機（640px 以下）改成卡片。

#### 主要技術選擇
- **查詢請求**
  - 同時只有一個查詢在進行，換條件時用 AbortController 取消舊的，避免舊結果晚回來蓋掉新結果。
  - 換條件時保留舊資料並變淡顯示，新的第一批回來才換掉，畫面不會閃成空白。
  - 載入失敗就停下來，顯示重試按鈕，不會自動一直重送。
  - 後端回 429 時，依 `Retry-After` 等一下再自動重試一次。
  - 第一批結果快取 30 秒，在幾個排序之間來回切換時不用重送。
  - 詳見 [ADR 0014](docs/adr/0014-request-lifecycle.md)。
- **分頁**：cursor 用「上一批最後一筆的排序值 + id」，捲動途中有人新增或刪除，下一批也不會漏掉或重複（[ADR 0013](docs/adr/0013-keyset-cursor.md)）。
- **多人修改**
  - 每筆資料帶版本號。有人先改過時後端回 409，前端列出「其他人改成 / 你要改成」，讓使用者選擇放棄、重新編輯或覆蓋。
  - 資料已經被別人刪除時，從列表移除並提示使用者。
  - 詳見 [ADR 0016](docs/adr/0016-create-and-conflicts.md)。
- **釘選**：在前端合併。後端給的是全域排序後的前 N 筆，在這 N 筆裡依位置插入，結果也是全域正確的；釘選後不用重新查詢，捲動位置也不變（[ADR 0015](docs/adr/0015-pin-on-frontend.md)）。
- **渲染**：虛擬捲動搭配 DOM 回收，桌機維持約 40 個列元素，避免捲動時反覆建立 DOM。和原本的實作比較，在快速捲動及包含元件的情境下有較好的效能，詳細比較記錄在 [ADR 0012](docs/adr/0012-dom-recycling.md)。代價是列高要固定，所以手機的卡片也是固定高度（[ADR 0017](docs/adr/0017-mobile-layout.md)）。
- **列表資料**：用 `shallowRef`，修改時換新陣列，避免上萬筆資料都被包成響應式物件。

#### 驗證
- `npm test`：49 項通過，涵蓋取消過期請求、失敗後不重送、載入途中刪除不漏資料、保留舊資料、快取、429、新增、409／404、釘選合併，以及 mock 的排序、搜尋與分頁。
- `node e2e/run.mjs`（Chromium）：23 項實際操作通過，包含 1920×1080 的完整流程（一千萬筆）、429 自動重試，以及 375×667 的手機版面。目前只在 Chromium 上測過。
- `npm run perf`（Node 22，一千萬筆）：mock 後端排序 180–620ms、搜尋 94–573ms，記憶體約 253MB。這是測試環境的成本，不是前端的數字。

#### 限制
- 一直往下捲，已載入的資料會一直累積（見 c 題）。
- 瀏覽器有捲動高度上限（Chrome 約 3,300 萬 px，桌機大約 75 萬列），其他瀏覽器的上限不同。
- 別人的修改，要等自己操作到那一筆或重新查詢時才會看到，沒有做即時推送。
- 多人衝突是用單元測試模擬的；mock 跑在每個分頁自己的 Worker 裡，開兩個分頁並不會共用資料。

### b. 搜尋請求從每分鐘 5 次暴增到 500 次

500 次／分鐘大約是每秒 8 次，不一定是異常流量，也可能是正常的使用量成長。所以短期會先確認請求增加的來源，再決定怎麼處理。

前端目前已經有的處理：
- 搜尋防抖 300ms，擋掉同一個人連續輸入造成的請求。
- 取消過期請求。
- 第一批結果快取 30 秒，擋掉在相同條件之間來回切換的請求。
- 失敗後不自動重送：重新審查時發現，原本載入失敗會一直重送請求，自己就會製造流量，這個問題已經修正。
- 後端限流回 429 時，依 `Retry-After` 等待後只重試一次。

如果主要是大量單字查詢，可以再評估限制最少搜尋字數，但 Age 這類欄位只有兩位數，不適合一律限制字數。如果是使用者數量增加，就需要後端配合快取及查詢最佳化。最少字數目前還沒實作。

### c. 使用者反映佔用太多 RAM

DOM 的部分已經處理：虛擬捲動加 DOM 回收，不管載入幾筆，畫面上都只有約 40 個列元素。資料也是一次只拿 500 筆，並用 `shallowRef` 避免每筆資料都建 Proxy。

還沒處理的是 JS 資料本身：一直往下捲，已載入的列會一直累積。如果要進一步改善，我會讓前端只保留最近約 10 批（5,000 筆），往回捲時再用 cursor 重新抓。cursor 已經改成 keyset，重新抓取時位置不會跑掉；但捲動高度和釘選列的合併也要跟著調整，所以目前先記在 [ADR 0011](docs/adr/0011-concurrent-users-frontend.md)，還沒實作。

# Q3

部落格後台的 wireframe，低擬真、灰階，數字都是範例資料。三個頁面共用左側導覽列，畫面上的橘色編號是設計說明的標記。

### Dashboard

![Dashboard](images/01-dashboard.png)

整頁共用右上角的時間區間，數字卡、趨勢圖、熱門收藏和最新動態都跟著同一個區間變，避免各區塊數字對不起來。每張數字卡都和前一段等長的期間比較，累計總數則獨立放一張卡，避免和區間數字混在一起。題目沒有審核流程，所以沒有做「待處理」區塊。

### User management

![User management](images/02-user-management.png)

左邊是使用者清單（可搜尋、依角色篩選、排序），右邊固定顯示選到的那個人的詳細資料，管理者可以一邊掃清單一邊看細節，不會被彈窗打斷。改角色前會先說明影響再確認，有未儲存的修改時切換使用者也會先詢問。頁尾有三種角色的權限對照表。

### User favorites management

![User favorites management](images/03-favorites.png)

用「使用者 → 資料夾 → 文章」三欄瀏覽，和資料本身的關係一致，上方路徑會顯示目前看的是誰的哪個資料夾。這頁只能看不能改，因為收藏是使用者自己整理的內容。

### 假設

題目沒有定義的部分，我在畫面上都有標示：管理者能進後台、修改角色、查看別人的資料夾；至少保留一位 Admin；帳號的 Status 欄位。另外沒有加入題目沒提到的指標或功能，例如轉換率、停權、新增帳號。
