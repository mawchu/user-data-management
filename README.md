# Q2. 使用者資料管理系統

線上 demo：<https://mawchu.github.io/user-data-management/>（網址加 `?size=5000` 會開得比較快）。程式碼導讀在 [docs/code-map.md](docs/code-map.md)，各項決定的考量記在 [docs/adr/](docs/adr/README.md)。

### a. 實作

使用 Vue 3 + TypeScript 完成新增、刪除、更新、搜尋、排序、釘選與無限捲動。因為沒有實際 API，我另外用 Web Worker 寫了一個能處理一千萬筆資料的 mock 後端。

主要處理幾個問題：

- 請求管理：搜尋防抖 300ms、取消舊請求、快取 30 秒，API 失敗後停止自動載入，避免一直重送。
- 大量資料：每次載入 500 筆，用 Keyset Cursor 避免資料增刪造成漏筆；虛擬捲動搭配 DOM 回收，減少渲染成本。
- 資料一致性：釘選在前端合併，不修改原始排序；多人修改則用 Version 檢查，遇到 409 讓使用者決定怎麼處理。

### b. 搜尋請求從每分鐘 5 次增加到 500 次

先確認請求增加的原因，不一定是異常流量，也可能是使用者變多。

前端已經做了搜尋防抖、取消舊請求和快取。另外，重新檢查時發現 API 失敗會一直觸發重送，反而自己製造流量，這部分已經修正。

如果是正常使用量增加，就需要後端配合查詢和快取優化。

### c. RAM 使用量過高

目前用虛擬捲動和 DOM 回收控制畫面上的元素數量，搭配 `shallowRef` 減少響應式開銷。

但一直往下捲，已載入的資料還是會累積。後續考慮只保留最近約 5,000 筆，往回捲時重新查詢，這部分還沒實作。

# Q3

部落格後台的 wireframe，低擬真、灰階，數字都是範例資料。三個頁面共用左側導覽列，畫面上的橘色編號是設計說明的標記。

### Dashboard

![Dashboard](images/01-dashboard.png)

整頁共用右上角的時間區間，數字卡、趨勢圖、熱門收藏和最新動態都跟著同一個區間變，避免各區塊數字對不起來。每張數字卡都和前一段等長的期間比較，累計總數則獨立放一張卡，避免和區間數字混在一起。題目沒有審核流程，所以沒有做「待處理」區塊。

### User management

![User management](images/02-user-management.png)

左邊是使用者清單（可搜尋、依角色篩選、排序），右邊固定顯示選到的那個人的詳細資料，管理者可以一邊掃清單一邊看細節，不會被彈窗打斷。改角色前會先說明影響再確認，有未儲存的修改時切換使用者也會先詢問。頁尾有三種角色的權限對照表。

### User favorites management

![User favorites management](images/03-favorites.png)

用「使用者 → 資料夾 → 文章」三欄瀏覽，和資料本身的關係一致，上方路徑會顯示目前看的是誰的哪個資料夾。這頁只能看不能改，因為收藏是使用者自己整理的內容。

### 假設

題目沒有定義的部分，我在畫面上都有標示：管理者能進後台、修改角色、查看別人的資料夾；至少保留一位 Admin；帳號的 Status 欄位。另外沒有加入題目沒提到的指標或功能，例如轉換率、停權、新增帳號。
