# Q2

Vue 3 + TypeScript 實作的使用者資料管理後台。重點放在前端：一次接 500 筆的無限捲動、資料量變大時維持順暢，以及刪除、更新、釘選的確認流程。

因為沒有真的 API，我另外寫了一個能撐一千萬筆的 mock 後端（放在 Web Worker），讓前端在接近題目的資料量下測試。接真 API 時刪掉 `main.ts` 裡的 `setupMock()` 即可。

程式碼導讀在 [docs/code-map.md](docs/code-map.md)，各項決定的考量記在 [docs/adr/](docs/adr/README.md)。

### a. 實作

#### 執行
```bash
npm install
npm run dev          # 開發模式，打開 http://localhost:5173
npm test             # 單元測試（33 項）
npm run perf         # 10,000,000 筆效能量測
npm run bench:scroll # 虛擬捲動三種寫法的效能比較（v1 / 簡單版 / DOM 回收）
npm run build && npm run preview   # 正式建置後預覽（http://localhost:4173）
node e2e/run.mjs     # 瀏覽器端對端測試（需先啟動 preview；Chromium 路徑用 CHROMIUM 環境變數指定）
```
除錯時可以在網址加 `?size=5000`，改用比較少的資料。

#### 功能
- 無限捲動：每次載入 500 筆，捲到離底部剩 150 列時先抓下一批。
- 刪除、更新都會跳確認視窗；更新會列出「原本 / 改為」再確認。前後端共用同一份欄位驗證。
- 一個搜尋框搜尋所有欄位（停止輸入 300ms 才查詢），點表頭可排序任一欄。
- 釘選：指定某筆資料固定在第幾列，之後不管怎麼排序都在那個位置。

#### 主要技術選擇
- 虛擬捲動搭配 DOM 回收，維持約 34 個列元素，避免捲動時反覆建立 DOM。和原本的實作比較，在快速捲動及包含元件的情境下有較好的效能，詳細比較記錄在 [ADR 0012](docs/adr/0012-dom-recycling.md)。代價是列高要固定。
- 列表用 `shallowRef`，修改時換新陣列，避免上萬筆資料都被包成響應式物件。
- 換搜尋或排序時用 AbortController 取消還沒回來的查詢，避免舊結果晚回來蓋掉新結果。更新、刪除這類修改請求刻意不取消，因為送出後後端可能已經改好了。
- 用 cursor 分批載入；刪除後 cursor 往前一格，避免下一批漏掉一筆。這個做法的前提是 cursor 代表位置，如果後端改用 keyset cursor 就不需要。

#### 驗證
- `npm test`：33 項通過（排序、搜尋、釘選、刪除、更新、取消請求）。
- `npm run perf`（Node 22，一千萬筆）：排序 189–450ms、搜尋 85–173ms，記憶體約 183MB。
- `node e2e/run.mjs`（Chromium，一千萬筆）：17 項實際操作通過，包含快速連點表頭會取消過期請求、DOM 回收、焦點保護。目前只在 Chromium 上測過。

#### 限制
- 一直往下捲，已載入的資料會一直累積（見 c 題）。
- 瀏覽器有捲動高度上限（Chrome 約 3,300 萬 px，大約 75 萬列），其他瀏覽器的上限不同。
- 沒有做新增資料（題目沒有要求）。

### b. 搜尋請求從每分鐘 5 次暴增到 500 次

500 次／分鐘大約是每秒 8 次，不一定是異常流量，也可能是正常的使用量成長。前端目前已經有搜尋防抖（300ms）和取消過期請求，可以擋掉同一個人連續輸入造成的重複請求，但擋不住使用者變多，或大家在相同條件之間來回切換。

短期會先確認請求增加的來源。如果主要來自重複搜尋，可以加上短時間快取；如果是大量單字查詢，再評估限制最少搜尋字數。這些都能先從前端調整，但如果是使用者數量增加，還是需要後端配合快取及查詢最佳化。快取和最少字數目前都還沒實作。

### c. 使用者反映佔用太多 RAM

DOM 的部分已經處理：虛擬捲動加 DOM 回收，不管載入幾筆，畫面上都只有約 34 個列元素。資料也是一次只拿 500 筆，並用 `shallowRef` 避免每筆資料都建 Proxy。

還沒處理的是 JS 資料本身：一直往下捲，已載入的列會一直累積。如果要進一步改善，我會讓前端只保留最近約 10 批（5,000 筆），往回捲時再用 cursor 重新抓。代價是往回捲要重新請求，捲動高度和刪除時的 cursor 修正也要跟著調整，所以目前先記在 [ADR 0011](docs/adr/0011-concurrent-users-frontend.md)，還沒實作。

# Q3

部落格後台的 wireframe，低擬真、灰階，數字都是範例資料。三個頁面共用左側導覽列，畫面上的橘色編號是設計說明的標記。

### Dashboard

![Dashboard](images/01-dashboard.png)

整頁共用右上角的時間區間，數字卡、趨勢圖、熱門收藏和最新動態都跟著同一個區間變，避免各區塊數字對不起來。每張數字卡都和前一段等長的期間比較，累計總數則獨立放一張卡，避免和區間數字混在一起。題目沒有審核流程，所以沒有做「待處理」區塊。

### User management

![User management](images/02-user-management.png)

左邊是使用者清單（可搜尋、依角色篩選、排序），右邊固定顯示選到的那個人的詳細資料，管理者可以一邊掃清單一邊看細節，不會被彈窗打斷。改角色前會先說明影響再確認，有未儲存的修改時切換使用者也會先詢問。頁尾有三種角色的權限對照表。

### User favorites management

![User favorites management](images/03-favorites.png)

用「使用者 → 資料夾 → 文章」三欄瀏覽，和資料本身的關係一致，上方路徑會顯示目前看的是誰的哪個資料夾。這頁只能看不能改，因為收藏是使用者自己整理的內容。

### 假設

題目沒有定義的部分，我在畫面上都有標示：管理者能進後台、修改角色、查看別人的資料夾；至少保留一位 Admin；帳號的 Status 欄位。另外沒有加入題目沒提到的指標或功能，例如轉換率、停權、新增帳號。
